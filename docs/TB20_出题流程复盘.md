# TB20 出题流程复盘

本文档记录本次 Terminal-Bench 2.0 风格题目从需求理解、选题、生成、验证、执行、日志采集、问题修复到最终打包的完整流程，并沉淀后续海量题库生产应遵守的标准。

## 1. 目标和约束

用户原始目标：

- 了解官方 Terminal-Bench 2.0 数据集格式。
- 给出至少一个场景下的三种难度数据集。
- 使用本地 Claude Code + Opus 4.7 运行。
- 必须采集 agent log。
- 不能过于简单，也不能和官方 demo 高度相似。

最终交付目标：

- 一个场景，三档难度：easy、medium、hard。
- 三档均符合 TB2.0 任务目录结构。
- 三档均可由 oracle solution 通过 verifier。
- 三档均由 Claude Code + Opus 4.7 实际运行并采集 agent logs。
- 三档最终 reward 均为 1。
- 剔除第一次 hard 失败数据，只打包最终通过版本。

## 3. 初版选题和复盘

初版选择 Apache/Nginx access log triage 场景：

- easy：解析 Common Log Format，输出 JSON。
- medium：解析 gzip 轮转日志，输出 CSV/JSON。
- hard：混合格式、坏行跳过、五分钟窗口和事件判定。

初版问题：

- 与官方 `nginx-request-logging`、`configure-git-webserver` 等 Web/server 类 demo 气质接近。
- 任务核心偏日志聚合，交付数据集样例辨识度不足。
- 难度上限不够高，容易被认为是普通脚本题。

结论：

```text
Apache/Nginx/log 分析不适合作为交付数据集。
```

## 4. 重新选题标准

为了避免偏离 TB2.0 初衷，又要体现交付数据集样例价值，选题遵循以下标准：

- 有稳定公开规范或公开许可数据源。
- 能在容器终端中真实完成，不是问答题。
- 需要 agent 读文件、写代码、生成输出、通过 verifier。
- 有可程序化验证的输出。
- 三档难度是能力梯度，不是同一任务简单放大。
- 和官方 demo 有明显区分度。
- 避免主观评分、实时网络依赖和不可复现数据。

最终选择：

```text
TZif / IANA zoneinfo 二进制格式取证
```

来源依据：

- RFC 8536 TZif format：https://www.rfc-editor.org/rfc/rfc8536.html
- IANA Time Zone Database：https://data.iana.org/time-zones/tz-link.html

选择理由：

- TZif 是真实二进制格式。
- IANA tzdb 是真实工程生态。
- 涉及二进制解析、64 位时间戳、post-2038、损坏文件、重复文件、DST gap/fold。
- 与 Web/server demo 明显不同。
- 可通过 JSON/CSV verifier 自动判定。

## 5. 三档难度设计

### easy: TZif v1 inventory

任务：

- 解析 `/app/zones/Example/Factory`。
- 读取 TZif v1 header、transition table、type table、abbreviation table。
- 输出 `/app/report.json`。

考察点：

- 二进制文件读取。
- big-endian 整数解析。
- type index 到 offset/DST/abbreviation 的映射。
- JSON schema 和排序要求。

### medium: TZif v2 UTC conversion

任务：

- 解析 `/app/zones/Lab/Eastern`。
- 必须跳过 v1 compatibility block，使用 TZif v2 64-bit block。
- 读取 `/app/queries.csv`。
- 输出 `/app/conversions.csv`。

考察点：

- TZif v2 双 block 结构。
- 64-bit transition time。
- transition boundary。
- post-2038 timestamp。
- UTC 到 local civil time 转换。

### hard: Zone bundle audit and local-time ambiguity

任务：

- 读取 `/app/bundle/`、`/app/manifest.csv`、`/app/local-events.csv`。
- 输出：

```text
/app/audit/zone_index.json
/app/audit/local_time_report.csv
```

考察点：

- 多文件 bundle audit。
- corrupt TZif 文件隔离。
- byte-for-byte duplicate zone 检测。
- TZif v2 解析。
- DST spring-forward gap 判定。
- DST fall-back fold 判定。
- local time 到 candidate UTC 的反向推理。


## 8. Claude Code + Opus 4.7 运行问题

第一次直接传：

```text
--model opus4.7
```

容器内 Claude Code 报错：

```text
API Error: 400 The supported API model names are deepseek-v4-pro or deepseek-v4-flash, but you passed opus4.7.
```

原因：

- 当前 shell 环境里 `ANTHROPIC_BASE_URL` 指向 DeepSeek 兼容 endpoint。
- 宿主机 `~/.claude/settings.json` 中真正的 Opus 4.7 配置是：

```text
ANTHROPIC_BASE_URL=https://ai.yiqiu.dev
ANTHROPIC_MODEL=claude-opus-4-7
```

修复方式：

- 使用完整模型名 `claude-opus-4-7`。
- 将宿主 Claude settings 中的 provider env 注入 Harbor 子进程。

执行脚本新增能力：

```text
--claude-settings-from-host ~/.claude/settings.json
--require-no-trial-exceptions
--require-reward 1
```

## 9. Harbor 执行流程

标准执行顺序：

```bash
python tools/tb20-production/scripts/tb20_execute.py init \
  --workspace <workspace> \
  --source-root <source-root> \
  --output-root <delivery-root> \
  --harbor /home/ubuntu/tb20-runtime/.venv/bin/harbor

python tools/tb20-production/scripts/tb20_execute.py deps --workspace <workspace>
python tools/tb20-production/scripts/tb20_execute.py inspect --workspace <workspace>

python tools/tb20-production/scripts/tb20_execute.py run \
  --workspace <workspace> \
  --agent claude-code \
  --model claude-opus-4-7 \
  --claude-settings-from-host ~/.claude/settings.json \
  --concurrency 1 \
  --force-build \
  --no-delete \
  --require-no-trial-exceptions \
  --require-reward 1

python tools/tb20-production/scripts/tb20_execute.py collect --workspace <workspace>
python tools/tb20-production/scripts/tb20_execute.py package --workspace <workspace>
python tools/tb20-production/scripts/tb20_execute.py audit --workspace <workspace>
```

重要经验：

- Harbor CLI exit code `0` 不代表 trial reward 为 1。
- 必须读取 trial `result.json` 中的 `exception_info` 和 `verifier_result`。
- 必须保留 `agent/claude-code.txt` 和 `agent/trajectory.json`。
- 本地任务应优先使用 `--force-build`，避免预构建镜像 tag 不存在导致 Docker pull 失败。
- 调试阶段使用 `--no-delete`，便于保留 job/trial 目录。

## 11. Hard 失败和微调

第一次 Opus 4.7 运行结果：

```text
easy   reward=1
medium reward=1
hard   reward=0
```

查看 hard agent log 后发现：

- 模型成功识别 corrupt file。
- 模型成功识别 duplicate zone。
- 模型成功识别 DST gap/fold。
- 失败来自 verifier 对 instruction 未明确要求的细节做了过窄断言。

具体不匹配：

1. `invalid_zones[].reason`
   - verifier 要求精确等于 `"truncated TZif data block"`。
   - 模型输出 `"truncated: missing v2 header"`。
   - instruction 只要求提供 `reason`，没有要求固定字符串。

2. `offsets`
   - verifier 只接受秒数 `-18000|-14400`。
   - 模型输出 ISO-style offset `-05:00|-04:00`。
   - instruction 没明确规定 hard 的 offset 单位或格式。

合理微调：

- `reason` 检查 path 正确，且 reason 包含 `truncated` 语义。
- `offsets` 接受秒数和 `±HH:MM` 两种等价格式。

没有放松的核心检查：

- corrupt zone path。
- duplicate group。
- version counts。
- candidate UTC。
- valid/nonexistent/ambiguous 分类。
- CSV/JSON schema。
- 排序和换行。

微调后 hard 重跑：

```text
hard reward=1
```

最终三档：

```text
easy   reward=1
medium reward=1
hard   reward=1
```

## 13. 是否偏离 TB2.0 初衷

判断：

```text
没有明显偏离 TB2.0 初衷。
```

原因：

- 任务在容器终端中执行。
- Agent 需要真实读取文件、写脚本、生成输出。
- 输出由 verifier 自动判定。
- 任务 source-grounded，基于 RFC 8536 和 IANA tzdb 生态。
- 不是问答题，不依赖主观评分。
- 与官方 demo 有明显区分度。

边界说明：

- 这是 TB2.0-compatible 风格数据集，不是官方原始 TB2.0 数据集的一部分。
- 单场景三难度适合作为交付数据集样例；正式大规模 benchmark 仍需多领域、多任务类型、多隐藏变体。

## 14. 本次修复沉淀到两个 TB20 skill

### tb20-dataset-production

新增规则：

- 交付数据集样例不能选择和官方 demo 高度相似的 Web/Nginx/log 简单场景。
- 优先选择规范驱动、格式驱动、多文件审计、二进制解析、恢复/验证类任务。
- 三档难度必须是能力梯度。
- verifier 不能检查 instruction 未声明的精确字符串、单位、offset 格式。
- exact output 要求必须写进 instruction。
- oracle 必须先跑。
- 注意 zsh 中 `$diff:local` 会被错误解析，必须写 `"${diff}:local"`。

### tb20-batch-execution-delivery

新增规则：

- `agent-logs/claude-code.txt` 必须采集。
- Harbor CLI exit code `0` 不等于 trial 成功。
- 必须读取 `exception_info` 和 reward。
- 支持 `--claude-settings-from-host`。
- 支持 `--require-no-trial-exceptions` 和 `--require-reward 1`。
- 支持当前 Harbor trial layout。
- 失败 evidence 可以采集，但 all-green delivery 不能打包模型/API 配置失败。

## 15. 海量题库生产方法

高产题库不应让模型随机发散，而应使用组合空间。

推荐坐标系：

```text
领域轴：文件格式 / 网络协议 / 数据库 / 系统运维 / 安全 / 科学计算 / 数据处理
对象轴：日志 / manifest / 二进制文件 / 配置 / 时间序列 / 图 / 表格 / 归档
操作轴：解析 / 校验 / 修复 / 转换 / 对账 / 分类 / 聚合 / 调度
约束轴：损坏 / 缺失 / 重复 / 边界时间 / 大文件 / 排序规则 / 精度容差 / 兼容版本
输出轴：JSON / CSV / patch / report / generated files / CLI behavior
```

推荐流程：

```text
1. source catalog
2. problem card
3. difficulty expansion
4. instruction
5. fixture generator
6. oracle solution
7. verifier
8. oracle run
9. target model run
10. agent log collection
11. package/audit
12. failure taxonomy feedback
```

优先扩展方向：

- binary formats：PNG、WAV、ZIP、TAR、SQLite page、TZif、ELF subset
- config/manifests：systemd unit、Kubernetes YAML、OCI manifest、package lock、GitHub Actions
- time/logs：rotation、timezone、clock skew、incident timeline、audit trails
- data validation：schema drift、CSV normalization、JSONL aggregation、duplicate detection
- security defensives：SBOM audit、weak config detection、CVE range matching、secret redaction
- graph/dependency：topological order、cycle detection、dependency impact、rollout planning
- scientific/numeric：tolerance checks、matrix metadata、signal windows、unit conversion

核心策略：

```text
有限场景模板 x 多学科组合 x 自动 fixture x 自动 verifier x 模型实跑筛选
```

## 16. 最终结论

本次出题流程形成了一个可复用闭环：

```text
官方格式确认
-> source-grounded 选题
-> 三档难度设计
-> 生成 instruction / fixture / oracle / verifier
-> oracle 先验
-> Harbor + Claude Code + Opus 4.7 实跑
-> agent log 采集
-> verifier/spec 一致性修正
-> package/audit
-> final tarball
-> skill 规则沉淀
```

该流程后续可以作为 TB2.0 风格题库批量生产的标准作业流程。
